# Human setup for Ground Control

Ground Control is hosted at `https://ground-control-washu26.azurewebsites.net`. The target repository does not need Azure hosting. Ground Control publishes its flightchecks when documentation changes and repairs older duplicate plans on server startup.

To publish a reviewed server or web fix, push its merged commit to this repository's `main` branch. `.github/workflows/deploy-azure.yml` builds and deploys that commit automatically. Verify the workflow succeeded and `/healthz` returns `ok`; the local Docker image does not update Azure by itself.

## Fast path for deep checks

A green Ground Control status means no **confirmed** documentation check failed. A first-run failure is disputed and needs an owner to review it on the linked run page; choose **Confirm** if the check is valid, then **Draft line edits** for a confirmed failing README or docs claim. GitHub's separate dependency and npm audit jobs must be resolved in the target repository's security workflow. This clarification requires no new credential or setup step.

To clear a repository's **Recent runs** list, sign in with a GitHub account that administers that repository, open its repository page, expand the details, and choose **Clear run log**. Confirm the prompt. The current result and existing run links remain available; subsequent runs appear in the list.

The signed-in **My repos** page shows how many repositories have reported deep checks. Use its **Deep checks set up** filter to see them together. A repository marked **Deep checks enabled · awaiting CI result** has no saved Action report yet; open its setup instructions and run the draft test PR if needed. Repository pages and **My reports** show the latest saved CI result separately from public README scans. An older CI report confirms that reporting worked at that time; check the repository's current workflow and Actions secret in GitHub if a later run stops arriving.

1. Open the hosted **Connect a repository** page, choose a repository you administer, and enable deep checks.
2. Copy its one-time telemetry token. Run the page's `gh secret set GROUND_CONTROL_TOKEN -R <owner/repo>` command and paste the token when prompted. The token does not appear in the command.
3. Choose **Add workflow to GitHub** to commit `ground-control.yml` to the target repository's default branch. This requires the server's `GITHUB_WRITE_TOKEN` to have Contents write access. Existing workflow files are left unchanged. Or choose **Download workflow** and add it yourself at `.github/workflows/ground-control.yml`. The file calls this repository's reusable workflow, which runs the flightchecks and reports to the hosted HTTPS server. Ground Control publishes the generated `flightchecks/` files on the target default branch.

The local checkout command is a fallback when automatic publication fails. The remaining steps below cover local development and optional integrations.

Ground Control also runs locally with Docker Desktop. Add local development keys to the ignored `.env` file in this repository; Azure uses Key Vault references for production credentials. Never put a credential in Git, a README, an issue, or a screenshot. You can run the web app and the bundled Orbit drift fixture before creating any account. Ordinary public scans use static and optional AI checks without executing repository code. A private repo you connect or a public repo owned by your signed-in GitHub account can use deep checks after explicit Actions setup.

For a public README scan you own, make sure its default branch has a root Markdown README, then sign in with the repository owner account and open its findings. **Fix with a pull request** drafts a correction from cited README lines and opens a draft PR for your review; **Ignore** removes a finding from the active checklist. Fix requires repository write access plus the configured model key. Review every proposed edit before merging it. The same actions are available on the full run page; no separate Ground Control account setup is needed.

The Sky uses steady dot brightness and slow position changes. Rebuild the Docker image after updating the app to receive the reduced-flicker map; no new key or account setup is required.

The desktop Sky map expands to match a taller selected-repository panel, removing the blank area below the map. The mobile layout keeps its stacked map size; no additional setup is required.

From an eligible repository's findings or its card in **My reports**, choose **Add deep scan** to open its prefilled Connect flow. When deep checks are enabled but no CI result has arrived, the page says so and **Review deep check setup** opens the existing instructions without requesting a new token. After an authenticated Action report arrives, the page shows that deep checks are set up, the latest CI verdict, and a link to its evidence. A public README scan alone does not verify the Action setup. If the old token was lost, expand **Lost the Actions token?** in Connect and issue a replacement, then update that repository's Actions secret.

After installing the workflow on the target repository's default branch, publishing `flightchecks/`, and adding its `GROUND_CONTROL_TOKEN` Actions secret, choose **Create test PR** on the Connect setup page. The server's `GITHUB_WRITE_TOKEN` needs Contents and Pull requests write access to that repository. The regular PR has an empty commit and no file edits; review its Actions jobs, then close it. The existing PowerShell `gh` command remains a local fallback. A repository without a root Markdown README or another registered documentation source cannot publish a useful flight plan; add a source and refresh it before the smoke PR.

For a confirmed failing deep CI finding with an exact README or `docs/` line citation, choose **Draft line edits** on its run page. A configured Anthropic or Gemini key proposes a cited Markdown change and opens a draft PR. Review each line in GitHub's Files changed view; merge or close the draft to accept or reject it. A same-repository source PR gets a draft against its head branch. Public README scan and deep CI draft bodies identify their source. CI determines whether a proposed edit passes.

Report mode rejects telemetry when its repository, commit SHA, or PR number differs from GitHub's workflow context. The check results are produced in the connected repository's CI checkout, so keep the Ground Control status advisory for branches whose authors can edit the generated runner until trusted attestation is added. A documentation change on the default branch queues immediate source refresh; PR branch documentation needs a manual refresh or a reviewed `seed-plan` commit before relying on new checks.

For the first live PR test, make sure a baseline run has passed or confirm the initial claim in Ground Control. A first failing claim is a review item and does not create a drift comment. A later failure of a confirmed claim can produce a PR comment with the cited claim, expected value, and observed evidence when `GITHUB_WRITE_TOKEN` is configured. The Action does not itself write a suggested fix into the PR. The current `FIX` reply path can open a correction draft only for a supported, cited server-port change; other failures need a manual documentation or code change. The local `bun run gc` and `bun ops seed-plan` commands remain optional owner-controlled fallbacks.

On the latest deep CI run, an admin can choose **Draft line edits** for a confirmed failing claim. This requires the signed-in GitHub OAuth token to write to the repository and either `ANTHROPIC_API_KEY` or `GEMINI_API_KEY` on the server. Ground Control checks the cited README or docs line against the commit before opening a draft PR with proposed line edits in **Files changed**. Review or revise those lines before merging; a draft proposal is not a verified correction, and the CI run on the draft may still use the old flight plan until the default-branch source refresh. When evidence is too weak for a grounded edit, the button reports that no edit is available.

The reusable workflow reports same-repo PRs only; fork PRs are skipped even if GitHub is configured to pass secrets to forks. A missing `GROUND_CONTROL_TOKEN` fails the report job. The server needs `GITHUB_WRITE_TOKEN` to look up the actual commit's GitHub author before sending iMessage. Without it, telemetry remains stored, but status, PR comment, and alert delivery are unavailable. If GitHub cannot identify a linked author, the stored run and available PR comment remain, but no alert goes to the PR opener or a name supplied in telemetry. Deep checks are also available in an owner-approved local checkout through `bun run gc scan --owned <checkout>`; GitHub Actions is the route for automatic PR checks and comments. The app does not create a repository secret; an admin can add the generated workflow through the Connect page or commit the downloaded file manually.

No GitHub repository webhook is needed for the iMessage path. The installed Actions workflow reports check results to `/api/telemetry`; the server resolves the checked commit's author through GitHub's API, then sends through Photon's cloud iMessage stream. Photon credentials and a provisioned line are separate from GitHub setup. If a message fails to send, a later retry of the same telemetry can retry its alert. Read-only phone replies can be retried after a send failure; mutating replies remain deduplicated to avoid repeating a fix or trust change.
